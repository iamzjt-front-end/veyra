# Authentication and secret handling

Veyra uses environment credentials for API adapters and the installed provider's native authentication for CLI adapters. It does not copy browser sessions, inspect native credential files, create a credential database, or save keys in `veyra.yaml` or `.veyra/`. Configure authentication before running a workflow. Missing credentials are reported as setup failures; Veyra never substitutes another account or provider silently.

## Credential selection

| Provider            | Source used by Veyra                                                            | Readiness scope                                                                                  |
| ------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `openai`            | Explicit `apiKeyEnv`, otherwise `OPENAI_API_KEY`; official Responses endpoint   | Environment presence only                                                                        |
| `claude`            | Explicit `apiKeyEnv`, otherwise `ANTHROPIC_API_KEY`; official Messages endpoint | Environment presence only                                                                        |
| `gemini`            | Explicit `apiKeyEnv`, otherwise `GEMINI_API_KEY`; Developer API                 | Environment presence only                                                                        |
| `openai-compatible` | Explicit `apiKeyEnv`; omitted means no authentication header                    | Explicit endpoint configuration and optional credential presence only                            |
| `codex`             | Native Codex environment/configuration/login                                    | Bounded version and native login-status command                                                  |
| `claude-code`       | Native Claude Code environment/configuration/login                              | Bounded version, flag and native auth-status commands                                            |
| `gemini-cli`        | Native Gemini CLI environment/settings/login                                    | Bounded version/flag checks and environment hints; offline native login validity remains unknown |
| `opencode`          | Native OpenCode environment/configuration/login                                 | Bounded version/flag checks; authentication and model access untested                            |

Provider namespace options are overridden by agent options; an explicit agent `model` overrides an option-level model and the binding supplies `id`. For API adapters, selecting `apiKeyEnv` fully replaces the default variable. A missing selected value does **not** fall back to another variable, native login, or an SDK's ambient credential discovery. `openai-compatible` never borrows `OPENAI_API_KEY` unless it is explicitly named. Standard native CLI auth precedence remains the installed tool's responsibility; Veyra does not introduce a universal env-versus-login override for those tools.

The API factories pass the same environment to readiness and execution. Programmatic API callers can inject `env`; omitting it uses `process.env`. Native CLI adapters inherit the actual process environment through Runtime and retain their native auth settings. Their optional injected `env` is used for diagnostics/redaction; use an injected `ProcessRunner` to control a test child's execution environment. Authentication is never a command-line secret argument generated by Veyra.

```yaml
plugins:
  openai:
    options:
      apiKeyEnv: TEAM_OPENAI_CREDENTIAL
agents:
  planner:
    provider: openai
    model: your-accessible-model
    options:
      role: planner
      # Overrides the namespace variable for this binding only.
      apiKeyEnv: PLANNING_CREDENTIAL
```

Set the variable through your shell/secret manager; the YAML stores only its name. Config parsing rejects credential-shaped option fields (including nested keys/tokens/passwords/cookies/private keys and `env`/`environment` snapshots). `apiKeyEnv` must be a valid variable name, up to 128 characters. The parser performs no environment lookup and does not echo rejected values. Do not put credentials into arbitrary model names, instructions, workflow identifiers, endpoint paths or third-party options to bypass this rule. Native provider credential/config files remain outside Veyra's managed state.

## Readiness is scoped evidence

`ve doctor --json` reports whether selected variables are present, which native checks passed, and what remains untested. It prints names and safe messages, never credential values or raw login output. Configuration presence does not prove a key is valid, a model is accessible, a local model is loaded, or an inference request will succeed. A native login-status success is also narrower than a successful model invocation.

An injected SDK client reports unknown authentication because it owns transport/authentication. The CLI never injects such clients in normal operation. API SDK calls disable their own diagnostic logging and retries; errors are normalized without raw response bodies or SDK/transport exception text. See each provider's reference for its actual request and failure behavior.

## Redaction boundaries

`@veyraoss/runtime` exports `collectSecretValues`, `createSecretRedactor`, `isSecretField` and `SecretRedactor`. These helpers are provider-neutral and require explicitly supplied values/environment; they do not read global state or files. The shared utility covers current Core, CLI, Verifier and provider output paths. TUI/Dashboard log renderers remain unimplemented and require their own integration verification when those milestones become eligible.

The helper collects recognized credential variable names, including generic `*_TOKEN`, API keys, access keys/IDs, passwords, credentials and private keys. Callers may add unusual variable names or explicit values. Text redaction replaces exact known values, JSON-escaped and doubly escaped representations, canonical URL-encoded variants, and Bearer diagnostics. Longer values are processed first and existing `[REDACTED]` markers remain stable. JSON redaction also masks credential-shaped fields and environment snapshots, and filters credential values embedded in payload object keys, without mutating caller data or token-usage counters. Masked payload keys may collide; redacted evidence does not preserve secret-keyed dictionaries as an executable data structure.

API input/output and native adapter prompts/bounded diagnostics use the helper. CLI display uses the known values from the environment plus every configured agent/namespace `apiKeyEnv`. The local run store receives those values ephemerally, redacts before writing/publishing/feeding later context, and preserves schema-defined workflow maps. It refuses redaction that corrupts structural control fields or changes a workflow/state map key; secrets cannot be used as execution identifiers. Workspace locations also cannot be silently redirected by redaction. A workflow step named `token` is still a step; a payload field carrying an auth token is redacted.

Programmatic Core/store callers must supply their own `redactValues`, including custom secrets, and configure injected stores directly. Core does not import a provider or inspect global credentials. For example:

```ts
import { collectSecretValues } from "@veyraoss/runtime";
import { VeyraEngine } from "@veyraoss/core";

const engine = new VeyraEngine({
  redactValues: collectSecretValues(process.env, ["MY_UNUSUAL_CREDENTIAL"]),
});
```

Known-value redaction is a defensive boundary, not a license to send secrets to agents. It cannot recognize every unknown secret, arbitrary encoding, partial value, or secret stored only inside native authentication/config files. It does not sanitize files written directly by executors, native session histories, third-party `console` output, or external service logs. Trusted plugin authors must follow the same no-secret-output/state rule and use environment indirection; Veyra's in-process plugin contract is not a sandbox. Review native tool permissions before execution and rotate any credential that was actually exposed.

## Recognizable token patterns and bounded diagnostics

Text filtering also masks conservative recognizable shapes: `sk-` key families, GitHub token prefixes, Google `AIza` keys, Slack `xox` tokens, AWS `AKIA`/`ASIA` access key IDs, three-part JWT-like tokens, PEM private-key blocks, Bearer diagnostics and Basic authorization headers. These are heuristics, not credential validity checks or an exhaustive inventory of provider formats. Unrecognized opaque values still require explicit environment-name/value configuration. Ordinary usage counters, short example labels and non-secret text remain intact; text that resembles a credential may be masked conservatively.

Call `redactor.text(retainedOutput, { truncated: true })` when an output buffer retained only a prefix. It removes the longest known credential/encoded-variant prefix at that boundary, including a complete value ending there. Prefix matching is linear in the inspected secret/output suffix lengths, and existing markers stay stable. This may conservatively mask an unrelated suffix that happens to match a secret prefix. `json` and Core's store honor sibling `stdoutTruncated`/`stderrTruncated` flags (and other corresponding `<field>Truncated` flags) for string fields.

Native CLI adapters pass actual truncation flags into diagnostic redaction. Core uses `store.redactText()` on complete provider/verifier exception messages before making 2,048-character excerpts, so clipping cannot expose a formerly recognizable secret fragment. Other context/CLI previews come from already sanitized persisted evidence. Neither path claims to reconstruct unknown values from arbitrary partial or independently streamed fragments.

`ShellVerifier({ redactValues? })` filters returned stdout/stderr/errors and its emitted command/output evidence. It also collects recognized credentials from an explicitly supplied `VerificationRequest.env`; it does not inspect ambient credentials. The original command and environment still reach the process as authorized by the caller. Never put secrets into shell text or execution identifiers. Core applications continue to supply all known values to the store for the final event/persistence boundary.

The changes apply when Veyra creates evidence and when CLI display uses the shared helper. Historical files are not rewritten as a migration; sanitize historical exports before sharing them. Files/artifacts written directly by an agent, native histories, raw Runtime streams and arbitrary plugin console output remain outside managed filtering. The planned TUI and Dashboard must render sanitized Core events and apply the same helper to any additional diagnostics; their renderer-specific tests cannot run while those surfaces are still scaffolds.

## Verification

Deterministic tests verify configuration rejection, explicit/default/no-auth selection, consistent OpenAI factory credentials, native auth preservation, safe doctor output, overlapping/escaped credential redaction, unchanged usage/structural fields, credential-free CLI/persisted failure evidence, recognizable unknown token formats, payload object keys, partial retained credentials and exceptions clipped at the diagnostic boundary. These tests use fixture secrets, fake SDK transports and isolated temporary state; they never require a real provider key or login.
